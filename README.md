# PART 1 — INGESTION

## 1.1 `documents.create` — file upload

```python
res = r_client.documents.create(request={
    "file": {
        "file_name": "example.pdf",       # REQUIRED — drives parser/type detection via extension
        "content": open("example.pdf", "rb"),  # REQUIRED — file-like object or bytes
    },
    "name": "Q3 Report",                  # optional — display name shown in dashboard/citations, independent of file_name
    "metadata": {"author": "Adeel"},      # optional — dict of str -> (str|bool|int|float|list)
    "partition": "server_123",            # optional — isolation boundary, see §1.6
    "external_id": "your-own-id-here",    # optional — YOUR id for this doc, for dedup/lookup, see §1.5
})
```
Also available: `create_async` (same signature, for use in async code — this is what you want in your bot).

**Response shape:**
```json
{
  "id": "21881de1-65f7-4816-b571-3ef69661c375",
  "created_at": "2024-07-05T22:21:21.099975Z",
  "updated_at": "2024-07-05T22:21:37.521837Z",
  "status": "ready",
  "name": "example.pdf",
  "metadata": {"author": "Adeel"},
  "chunk_count": 86,
  "external_id": null
}
```
`res.id` is your `content_id` — generated by Ragie, GUID, returned synchronously regardless of how long processing takes.

**Precautions:**
- `file_name` is required in every example I found — no way to omit it. It's not cosmetic: the extension is how Ragie picks a parser. Auto-generate one (`f"{uuid.uuid4().hex}.pdf"`) if you don't want to manage real filenames — see §1.7 for the `name` vs `file_name` split.
- Supported file types list lives in the API reference itself — check there directly for anything unusual (e.g., specific spreadsheet or email formats) rather than assuming.

## 1.2 `documents.create_raw` — raw text ingestion

```python
res = r_client.documents.create_raw(request={
    "data": "Some FAQ text here",   # REQUIRED — the raw text itself
    "name": "faq-snippet",          # optional
    "metadata": {"source": "faq"},  # optional
    "partition": "server_123",      # optional
})
```
Same response shape as `create`. Use this for your `add_text_graphlit` equivalent — no fake filename needed since there's no file involved.

## 1.4 Ingest modes (`fast` / `hi_res` / Agentic OCR)

⚠️ **Exact parameter name for setting mode on `documents.create` not independently confirmed** in the snippets I pulled — the concept is well documented (mode affects both cost and extraction quality), but I did not see the literal field name (likely `mode`, based on connector-config language) in an isolated `documents.create()` code sample. Confirm the exact key in the API reference before setting it, rather than guessing.

What the modes mean regardless of exact param name:
| Mode | Behavior | Cost/speed |
|---|---|---|
| `fast` (default) | Extracts text only, misses charts/tables/images | Fastest, cheapest — can be up to 20x faster than hi_res |
| `hi_res` | Uses multi-modal LLMs + OCR to pull structured data from charts, graphs, tables, images | Slower, pricier |
| Agentic OCR | Vision-model-based, best for low-quality scans, forms, inconsistent layouts | Highest cost, most accurate |

**Precaution:** PDFs over 2000 pages are not supported in `hi_res` mode — if you're ingesting long PDFs, either use `fast` mode for those or chunk the PDF yourself before upload.

## 1.5 `external_id` — your own reference ID (dedup)

You can pass your own `external_id` alongside Ragie's generated `id`. This is how connector pipelines (e.g., the Airbyte destination) implement dedup — supplying the same `external_id` on a re-sync updates the existing document instead of creating a duplicate.

**Practical use for your bot:** if you ever re-ingest the same source (e.g., re-scraping the same website URL on a schedule), pass a stable `external_id` (like a hash of the URL) so repeated ingestion updates the existing doc instead of piling up duplicates. Without this, your website/GitHub re-crawl logic will create a new document + new ID every single run.

## 1.6 Partitions

```python
res = r_client.documents.create(request={
    "file": {...},
    "partition": "server_123",   # your Discord server_id — hard isolation boundary
})
```
- Documents in different partitions cannot leak into each other's retrieval results — this is stronger than a metadata filter, it's a structural boundary.
- **Account-age caveat:** accounts created after Jan 9, 2025 default to the `"default"` partition if you omit this param. Accounts older than that default to searching **all partitions** if omitted. If your account predates that date, you must opt into strict partition scoping via `support@ragie.ai`, or every request that omits `partition` will silently search across every server's data.
- Partition names must be lowercase alphanumeric, with `_` and `-` allowed — validate your `server_id` format matches this before using it directly as a partition key.

## 1.7 `name` vs `file_name` vs `metadata`

Three separate places information can live, don't conflate them:
- `file.file_name` — internal, drives parsing, never has to be meaningful
- `name` — the human-readable label shown in dashboard/citations
- `metadata` — arbitrary structured data for filtering later (e.g., `server_id`, `channel_id`, `source`)

## 1.8 Updating an existing document

```python
res = r_client.documents.update_file(
    document_id="00000000-0000-0000-0000-000000000000",
    update_document_file_params={
        "file": {"file_name": "example.pdf", "content": open("example.pdf", "rb")},
    },
    partition="server_123",
)
```
**Precaution:** updating a document's file **regenerates all its chunks**, including their index numbers. Any chunk IDs you've cached elsewhere become stale after this call.

## 1.9 Updating metadata only (no reprocessing)

```python
res = r_client.documents.patch_metadata(
    document_id="00000000-0000-0000-0000-000000000000",
    patch_document_metadata_params={
        "metadata": {
            "classified": None,        # setting a key to null DELETES it from metadata
            "editors": ["Alice", "Bob"],
            "published": True,
            "articleCount": 42,
        },
    },
    partition="server_123",
)
```
- Does **not** trigger re-chunking/re-indexing — pure metadata patch, cheap and fast.
- Setting a key's value to `null` deletes that key entirely, doesn't just blank it.
- **Reserved keys:** any metadata key starting with an underscore (`_name`, etc.) is reserved internally — attempting to set one returns a **422 error**.
- **Max 1000 values per metadata object.**
- If this document is connector-managed (synced from Google Drive/Notion/etc.), patching metadata creates a **Metadata Overlay** — your manual edits survive future automatic syncs instead of getting silently overwritten.

## 1.10 Checking document status

```python
doc = r_client.documents.get(document_id="21881de1-65f7-4816-b571-3ef69661c375")
print(doc.status)
```
Status values: `pending`, `partitioning`, `partitioned`, `refined`, `chunked`, `indexed`, `summary_indexed`, `keyword_indexed`, `ready`, `failed`, and `paused_insufficient_credits` (fires if your account runs out of credits mid-processing — this is a real production gotcha, set balance alerts).

**Alternative to polling:** subscribe to webhooks for status-change events instead of polling in a loop — see the earlier reference doc for webhook signature validation.

## 1.11 Deleting a document

```python
r_client.documents.delete(document_id="...")
```
**Precaution:** if the document is **connector-managed** (synced from an external source), attempting to delete it via the API now correctly returns a **409 Conflict** with a descriptive error, rather than the undefined behavior/data inconsistency it used to cause. You cannot delete connector-managed docs directly — you manage them via the connection instead.

## 1.12 Listing documents

```python
res = r_client.documents.list(request={
    "filter_": '{"department":{"$in":["sales","marketing"]}}',  # note: JSON string, key is "filter_" not "filter"
    "partition": "server_123",
})
while res is not None:
    for doc in res.result.documents:   # exact accessor may vary by SDK version — check res shape
        print(doc.id, doc.status)
    res = res.next()   # pagination cursor pattern
```
**Precaution:** the parameter is `filter_` (trailing underscore) in the Python SDK's `list` request, not `filter` — this differs from the `retrievals.retrieve` call where it's just `filter`. Easy source of a silent bug if you copy-paste between the two.

## 1.13 Listing/fetching chunks directly

```python
res = r_client.documents.list_chunks(document_id="...", start_index=0, end_index=50)
```
- Paginated, max 100 per page, use returned cursor for more.
- **Precaution:** documents created before **Sept 18, 2024** and never updated since have chunks **without an index** — those chunks report `index: -1` and are sorted by chunk ID instead of position. Irrelevant for anything you ingest going forward, but matters if you ever migrate/import older Ragie data.

```python
content = r_client.documents.get_chunk_content(request={
    "document_id": "...",
    "chunk_id": "...",
    "media_type": ragie.MediaType.TEXT_PLAIN,
    "partition": "server_123",
})
```

## 1.14 Fetching full document content / original source file

```python
r_client.documents.get_content(document_id="...")   # parsed content, add media_type param for other formats
r_client.documents.get_source(document_id="...")     # the ORIGINAL uploaded file/URL content/connector payload
```

# PART 2 — QUERYING (RETRIEVAL)

## 2.1 `retrievals.retrieve` — the core call

```python
res = r_client.retrievals.retrieve(request={
    "query": "What are the contract terms?",   # REQUIRED — natural language query
    "partition": "server_123",                 # scopes to one partition
    "filter": {"document_id": {"$in": [id1, id2]}},  # optional metadata pre-filter, see §2.3
    "rerank": True,                            # optional, default varies — see §2.2
    "top_k": 8,                                # optional — number of chunks to return
    "max_chunks_per_document": 3,               # optional — caps chunks from any single doc
})
```
Also available: `retrieve_async` for your async bot code.

## 2.2 `top_k` and `rerank` — how they interact

- `top_k` sets how many chunks come back.
- When `rerank: True`, `top_k` becomes a **ceiling, not a guarantee** — reranking can filter out some results even if that many existed, since it's judging actual relevance, not just semantic similarity.
- Turning on `rerank` improves quality generally but adds latency, and can occasionally filter out chunks that would've been useful.
- **Practical tuning note directly from Ragie's own guidance:** higher `top_k` increases the odds a given relevant chunk gets returned, but costs more latency and LLM tokens downstream — there's no universal right value, test against your actual queries.

## 2.3 `filter` — metadata pre-filtering

```python
{"genre": "comedy"}                                   # exact match
{"genre": {"$in": ["documentary", "action"]}}          # any-of match
{"$and": [{"genre": "comedy"}, {"year": {"$gte": 2020}}]}  # combine conditions
{"source": {"$eq": "sharepoint"}}                      # explicit equality (same as bare value)
```
Confirmed operators: `$in`, `$and`, `$eq`. Standard Mongo-style operators (`$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$nin`) are the typical set for this style of filter syntax elsewhere, but I did not independently confirm each of these specifically for Ragie — verify against the metadata-filters doc page before relying on any operator beyond the three confirmed above.

**Precaution:** filtering is a **pre-filter**, meaning it guarantees your `top_k` results *do* exist within the filtered set if they're there — **except when `rerank` is on**, where reranking is capped at `top_k` results regardless.

**Default metadata fields present on every document automatically** (usable in filters without you setting them): `document_id`, `document_type` (`pdf`, `doc`, `docx`, `img`, `jpg`, etc.), and others not fully captured in what I pulled — check the Metadata & Filters doc page directly for the complete default list before assuming a field exists.

## 2.4 Response shape — `scored_chunks`

```json
{
  "scored_chunks": [
    {
      "text": "...",
      "score": 0.1818,
      "id": "chunkId",
      "index": 0,
      "metadata": {},
      "document_id": "docId",
      "document_name": "TIGER",
      "document_metadata": {},
      "links": {
        "self": {"href": "...", "type": "application/json"},
        "self_text": {"href": "...", "type": "text/plain-text"},
        "document": {"href": "..."},
        "document_text": {"href": "..."},
        "self_image": {"href": "...", "type": "image/jpeg"}
      }
    }
  ]
}
```

Field-by-field:
- **`score`** — ⚠️ **relative to this single retrieval call only.** Do not compare scores across different queries, and do not hardcode a global "minimum score threshold" — Ragie's own docs explicitly warn against this. If you want a cutoff heuristic, look for a statistically significant drop within one result set, not an absolute number.
- **`index`** — position of this chunk within its parent document's chunk sequence.
- **`metadata`** — chunk-specific, **type-dependent**: audio/video chunks get `start_time`/`end_time`; PDF/PowerPoint chunks get `start_page`/`end_page`. Useful if you want to show "jump to this timestamp/page" in your bot's citation.
- **`document_metadata`** — the parent document's metadata (your `server_id`, `channel_id`, etc., if you set them at ingest time).
- **`links`** — direct URLs to fetch the chunk/document content in various formats (text, image, JSON) — handy if you want to let users click through to the source without you building that endpoint yourself.

## 2.5 Precautions specific to querying

1. **Don't query before a document is at least `indexed`.** Semantic search works from `indexed` onward, but hybrid (keyword) search only works from `keyword_indexed`, and full feature parity (including summary index) isn't guaranteed until `ready`. Race conditions are real if you let users query immediately after upload without checking status.
2. **`filter` key name differs between calls** — it's `filter` on `retrievals.retrieve` but `filter_` (with trailing underscore) on `documents.list`. Copy-paste mistakes between the two are an easy bug.
3. **Scores aren't comparable across calls or servers.** If you're logging/monitoring retrieval quality across different Discord servers, don't average or compare raw scores between them — normalize within each call instead.
4. **`max_chunks_per_document`** is worth turning on if your knowledge base has a few very large documents that could otherwise dominate every result set — it forces diversity across sources.
5. **No native chat/generation** — `retrieve` gives you chunks only. Every system-prompt/language/tone/citation-formatting decision is entirely your own code, same as we've built in your `ragie_query.py`.
